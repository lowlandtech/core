## Outcome and scope

Declare in the canonical Core contract how a host mounts the routes of a
declared endpoint group, so that a producer implements one member and a host
reads one member, instead of every host and every feature agreeing on an
undeclared convention.

This scope declares the contract. It does not implement a host runtime, it does
not migrate the feature groups of other lanes and it does not publish a
package on its own; the delivery of the declared contract ships with the next
immutable `LowlandTech.Core` version and the migration of the feature groups
stays with the lanes that own them.

## The gap, measured

`src/lib/Plugins/EndpointGroup.cs` documents the entry point without
declaring it:

> Implementations override `GroupPrefix` and provide a routing entry point.
> The host wires the group into the application route table during startup.

The class declares the metadata of the group — the prefix, the tags, the
authentication scheme and the policy — but no member that mounts its routes.
`IFeatureRegistrationBuilder.MapEndpoints<TGroup>(string featureId)` creates the
group and records an `EndpointGroupDescriptor` with that metadata, and the
descriptor carries no way to call the entry point.

The consequence is that the entry point exists only as a convention: the
Backend now calls `MapEndpoints(RouteGroupBuilder group, IServiceProvider
services)` on the group, and a host that reads the contract alone cannot mount
a declared group. The Builder reported the same gap.

## The Core decision

**Core declares the entry point on `EndpointGroup` in a framework-neutral
shape, and the host owns the route table.**

```csharp
public abstract class EndpointGroup
{
    // The metadata of the group, unchanged.
    public abstract string GroupPrefix { get; }
    public virtual string[] Tags => [];
    public virtual string? RequiredAuthenticationScheme => null;
    public virtual string? RequiredPolicy => null;

    /// The entry point the host calls to mount the routes of the group.
    public abstract void MapEndpoints(IEndpointGroupContext context);
}
```

The context is the host's own surface, so the contract names no web framework
type:

```csharp
public interface IEndpointGroupContext
{
    /// The services the host resolved for the group.
    IServiceProvider Services { get; }

    /// Maps one route of the group on the route table that the host owns.
    void Map(string method, string pattern, Delegate handler);
}
```

The rules of the convention:

1. The host owns the route table, the prefix, the tags and the protection. It
   creates the context over its own route builder and calls the entry point.
2. The group maps its routes onto the context and declares no framework type.
3. The declared metadata of the group stays in the descriptor, so a host knows
   the prefix, the tags and the protection of a group before it mounts it and
   can refuse a conflicting prefix as it does today.
4. The Backend's `MapEndpoints(RouteGroupBuilder, IServiceProvider)` is the
   Backend's own implementation of this convention: the Backend keeps its
   route builder, and the feature groups migrate to the declared member.

The shape is deliberately the smallest one that a host can implement and a
feature can use: the group maps routes, the host maps them onto its table, and
neither side names the other's framework.

## The compatibility consequence, stated

The declaration is a new member on an abstract class, so a feature group that
declares its own entry point today migrates to the declared member in the
source-owned scope of its own lane. Core claims no migration of the feature
groups of the Builder or the Backend.

The delivery ships with the next immutable `LowlandTech.Core` version. The
Components batch pins the Core package exactly, so the new version and the
batch that pins it move together, and the consumers move with them.

that own the half:

1. **The Builder does not break on the pin move.** Its `LowlandTech.Core`
   reference resolves to the project `src/shared/core/LowlandTech.Core.csproj`
   (`type: project` in every one of its nine resolved project graphs), not to
   the published package. The copy carries 121 files against the canonical 122:
   the only file it lacks is `IEndpointGroupContext.cs`, and its own
   `EndpointGroup.cs` carries no `MapEndpoints` member. Moving
   `BuilderCorePackageVersion` therefore changes nothing for the Builder's
   groups. What breaks the Builder is the re-copy of the canonical source into
   `src/shared/core`, which is the next block of `CANS2100-US60-SC02`: the
   re-copied `EndpointGroup` declares the abstract member, and the Builder's
   five concrete groups implement the old two-parameter shape.
2. **The Backend's host needs the new shape, not only its groups.**
   `PluginEndpointGroupMount.Resolve` selects a public instance method named
   `MapEndpoints` whose first parameter is a `RouteGroupBuilder` and whose
   second is an `IServiceProvider`. The declared member takes one parameter of
   the host context, so the Backend's host stops finding the entry point of
   every declared group unless the Backend adopts the declared shape in its own
   scope.

The Harness fork is not a second copy of the canonical type in this surface:
`src/core/Plugins/EndpointGroup.cs` declares `LowlandTech.Harness.Core.Plugins.EndpointGroup`,
a different namespace from the canonical `LowlandTech.Core.Plugins.EndpointGroup`,
and the Harness test project imports the canonical namespace globally. The
`SampleGroup` and `FakeEndpointGroup` classes of the Harness therefore bind the
canonical type through the package and break on the pin move.
