## Outcome and scope

Centralize only portable plugin identity, target, manifest/contribution and immutable binding contracts in a Core-produced package consumed by Plugins and Backend. Inventory the currently published Plugins Domain API before moving any type; preserve versioned manifests, package identity, content hashes and compatibility with existing deployed packages. Keep NuGet orchestration, activation registry, deployment verification, host dispatch and graph execution with their current owners.

## Acceptance criteria

- [x] UAC01: The shared contract describes a versioned backend-api or frontend contribution and its definition files without executable CLR type names supplied by untrusted data.
- [ ] UAC02: Plugins and Backend consume one exact contract package version; old published manifests remain readable or receive an explicit versioned migration/refusal.
- [x] UAC03: A package-only producer/consumer test verifies manifest, contribution ownership and content-hash validation without source checkout references.
- [x] UAC04: New contract assembly remains free of EF Core, NuGet runtime, ASP.NET and host activation dependencies.

### The portable declaration delivered — 2026-10-27

The portable target, manifest and contribution declarations are published in the
Core contract package. The declaration is data only, the reader resolves
nothing it reads, and the schema versions the published hosts use keep their
meaning.

| Type | Purpose |
|---|---|
| `PortablePluginTarget` | the two targets the published hosts already use |
| `PortablePluginTargetExtension` | the versioned extension of a target: `None`, `BackendApi`, `Frontend` |
| `PortablePluginTargetDeclaration` | the target as a versioned declaration |
| `PortablePluginManifestDeclaration` | the portable declaration of a manifest |
| `PortablePluginContributionDeclaration` | the thirteen contribution groups as keys |
| `PortablePluginInstallationUnit` | the required capabilities and contracts of the unit |
| `PortablePluginDependencyDeclaration` | a declared logical dependency |
| `PortablePluginRouteDeclaration` | a declared route |
| `PortablePluginSlotDeclaration` | a declared slot |
| `PortablePluginComponentPlacementDeclaration` | a declared component placement |
| `PortablePluginClientAssetDeclaration` | the declared client assets |
| `PortablePluginDefinitionFile` | a declared definition file with its content hash |
| `PortablePluginParameterValue` | a placement parameter as text, number, flag or null |
| `PortablePluginManifestValidator` | the reader of a manifest document |
| `PortablePluginManifestWriter` | the writer of a manifest document |

The versioned target: the two members the published hosts already use stay the
plain target, and a new backend api or frontend meaning is a versioned
extension of that target, so a host that predates the extension keeps reading
the older meaning of the same target.

The naming rule: every type carries the `Portable` prefix, so the package
publishes no name the Plugins host reserves to its own manifest model
(`PluginManifest`, `PluginContributions`, `PluginTarget`,
`PluginInstallationUnit`, `PluginDependency`, `PluginRoute`, `PluginSlot`,
`PluginComponentPlacement`, `PluginClientAsset`, `PluginClientAssets`,
`PluginPackageDescriptor`) and no name the Backend reserves to its host runtime.
The acceptance inventory of CORE0002-US01-SC01 now asserts both lists.
