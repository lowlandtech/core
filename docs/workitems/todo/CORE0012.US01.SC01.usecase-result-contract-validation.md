## The measured state

### The validator is alias-blind

`eng/verify-test-layout.py` matches the UAC trait with one literal pattern
(`_UAC_PATTERN`, line 72 of the current source):

```python
_UAC_PATTERN = re.compile(r"\[\s*Trait\s*\(\s*\"UAC\"\s*,\s*\"(?P<number>[^\"]*)\"")
```

The Builder declares the trait keys as constants in
`builder/src/testing/LowlandTech.Builder.Testing/Spec.cs` (`SPEC`, `US`, `SC`,
`UAC`) and writes `[Trait(Spec.UAC, "NN")]`. A measured scan of the tracked test
sources:

| Lane | Trait form | Occurrences | Files |
|---|---|---|---|
| Builder (`src/test`) | `Trait(Spec.UAC, ...)` | 2,646 | 678 |
| Backend (`src/test`) | `Trait("UAC", ...)` | 2,165 | — |
| Harness (`src`) | `Trait("UAC", ...)` | 818 | — |
| Components (`src`) | `Trait("UAC", ...)` | 17 | — |

Every Builder Fact therefore reports `missing-uac-trait` against the Core
checker, and the duplicate rule never runs for them. The same blind spot hides
the story trait when it is written with the alias.

### The namespace gap is repaired in the named file, not in the rule

`backend/src/test/CHAN0001.Channels/US01.Transport/SC02_DurableInbox.cs` now
declares `namespace LowlandTech.Specs.CHAN0001.Channels.US01.Transport;`, so the
file the coordinator named is no longer in the global namespace. The rule that
would have caught it is still absent: the Core gate checks the path shape and
the class name, and never reads the declared namespace. A scenario that loses
its namespace is still reported as a valid scenario.

### The Auth result surface is large and only partly mapped

Measured over `backend/src/test/AUTH0001.BackendAbsorption`:

| Measure | Value |
|---|---|
| UseCase classes | 72 |
| declared result members (`public ... { get; }`, `Diagnostics` excluded) | 535 (424 distinct names) |
| scenario files | 74 |
| `[Then(...)]` steps | 520 |
| distinct members read as `Result.<Name>` | 413 |
| declared members never read as `Result.<Name>` in the area | 12 |

The Then steps already name the observation (`[Then("Result.Pair should be
issued")]`), which is the de facto result contract of this area. What the
tooling does not do is check that mapping: a member that no Fact reads is
invisible, a Then step that names a member the UseCase does not declare is
invisible, and nothing requires the read to be the named result the graph would
explain.

### Refusals are statuses, not graph-explainable names

The Auth scenarios assert HTTP statuses and booleans for refusals
(`Result.WrongPassword` is `401`, `Result.UnknownIdentity` is `401`,
`Result.DisabledAccount` is `401`). The canonical graph contract already
publishes the named refusal vocabulary that the user direction asks for:
`LowlandTech.Core.Contracts.Transitions.TransitionContractDiagnostic` carries a
`Code` and `TransitionContractDiagnosticCodes` declares the stable `gs.*` codes
(`gs.contract.*`, and the capability admission code `gs.contract.capability.unknown`
proved in M3-004). A 401 can be produced by several causes and the graph cannot
explain which one, while a code names exactly one cause.

## The proposed validator contract

Five checks, each with the finding code it would emit. The checks run only on
the scopes an adopting lane opts into (see adoption below).

### V1 — alias-aware trait resolution

- **Rule:** resolve the trait key through the declaring constants of the scanned
  repository (a small, explicit alias table: `"UAC"`, `Spec.UAC`, and any
  `const string` whose value is `UAC`), then apply the existing UAC rules to the
  resolved value.
- **Finding:** none new; V1 removes the false `missing-uac-trait` findings so
  V2 can run.
- **Limit:** only compile-time constants are resolvable. An expression that
  builds the trait key at run time is reported as `unresolved-trait-key` rather
  than silently accepted.

### V2 — unique UAC per Fact, alias-resolved

- **Rule:** within one scenario, every Fact carries exactly one resolved UAC and
  no two Facts carry the same number, regardless of their descriptions. The
  grammar's rule is *one unique numeric UAC per Fact*, so a different
  description does not license the repeat.
- **Finding:** `duplicate-uac-trait`, with both line numbers.
- **Limit:** the rule is per scenario. A story that repeats a number across two
  scenarios is a separate decision (see open decisions) and is not reported by
  this check.

### V3 — the declared area namespace

- **Rule:** a scenario file declares a namespace, and that namespace starts with
  the repository's declared spec root and carries `<SPEC>.<Area>` as its first
  two segments after the root, matching the path.
- **Finding:** `missing-namespace` for a global-namespace scenario, and
  `namespace-area-mismatch` when the namespace and the path name different
  areas.
- **Limit:** a namespace filter can still miss a scenario whose namespace is
  spelled correctly but whose file name a filter does not select; the check
  proves the declaration, not the filter.

### V4 — UseCase result coverage

- **Rule:** for each area that opts in, the Checker reads the UseCase classes of
  the area and the `[Then]` steps of its scenarios. Every declared public result
  member must be read by at least one Then step (`Result.<Name>` or the
  configured observation accessor), and every Then step must name a member the
  UseCase declares. `Diagnostics` is the declared escape hatch and is exempt.
- **Findings:** `unread-use-case-result` (a declared branch no Fact observes) and
  `undeclared-use-case-result` (a Fact reads a member the UseCase does not
  declare).
- **Limit:** it is a *coverage* check, not a behavior check. It cannot prove that
  the observed value is the right one; the Fact's assertion still carries that
  proof. It also cannot see a result member whose type is not declared as a
  property (a field, a tuple through a method), so the adopters must keep the
  observation surface a property or extend the configured surface.

### V5 — named refusal reasons

- **Rule:** for each area that opts in, the Checker reads the declared reason
  vocabulary of the area's production contract and the Then steps. Every refusal
  branch the vocabulary declares must be asserted by its exact name in at least
  one Then step, and every named reason a Then step asserts must exist in the
  vocabulary.
- **Findings:** `unasserted-refusal-reason` and `undeclared-refusal-reason`.
- **Limit:** the check maps a vocabulary to a test; it cannot prove that the host
  returns that code on that path. That proof stays the behavior Fact. A lane
  whose production refusals carry no declared vocabulary reports
  `no-refusal-vocabulary`, which is the finding that names the real production
  gap rather than inventing a test-side reason.

## Adoption and baseline strategy

- **Opt-in manifest.** Each adopting lane adds a manifest entry naming its test
  root, spec root, observation accessor, result-type allowlist and reason
  vocabulary source. No lane is scanned by default; this creates no consumer
  approval gate and no cross-lane dependency.
- **Baseline file.** The first run of an adopting area records every finding in a
  committed baseline (`eng/test-layout/usecase-baseline.json`) with a reason per
  finding. The gate then fails only on a finding that is not in the baseline, so
  a lane can adopt without repairing its history in one pass. The baseline is a
  debt record, not a waiver: an entry that no longer matches a finding is
  reported as `stale-baseline-entry` and must be removed.
- **Burn-down order.** Core proves the checks on its own tree and its negative
  fixtures first, then the Backend Auth area is the pilot for V4/V5 because it
  is the area the user direction names, then the Builder for V1/V2 because it
  holds the measured alias and duplicate debt. The Harness and Components adopt
  V1/V2 with nothing to repair.
- **Core-owned fixtures.** Every check gets one positive and one negative
  fixture under `eng/test-layout/fixtures/`, plus one regression fixture per
  reported defect: the alias duplicate (PRB-040), the missing namespace
  (CHAN0001), the unread result and the unasserted reason.

## Risks and mitigations

- **The validator becomes a second contract producer.** Mitigated by reading the
  lane's declared vocabulary and UseCase surface and never re-declaring them in
  test tooling.
- **False positives on unfamiliar result shapes.** Mitigated by the opt-in
  manifest, the configured observation accessor and the baseline.
- **Enforcement racing a consumer lane.** Mitigated by the explicit non-goal: no
  lane is scanned until it opts in, and the proposal creates no dependency edge
  or approval gate.
- **Baseline decay.** Mitigated by `stale-baseline-entry`, which fails when a
  recorded finding disappears and the entry is not removed.
- **The named reason is invented at test time.** Mitigated by V5 refusing to
  pass an area that has no declared vocabulary.

## Verification and recovery

- Each check runs against its positive and negative fixtures; the fixture run is
  the validator's own acceptance and is recorded with the check's code.
- The existing layout checks keep their current results: the Core tree reports
  12 scenarios, 0 legacy test files and 0 violations before and after V1-V3.
- The adopting lane records the exact command, exit code, selected areas and the
  baseline diff.
- Recovery is one revert of the manifest entry and the baseline file; no
  production code, API or package is touched by any check.

## Open decisions

1. **Who owns the runtime reason vocabulary** — the Core contract already
   publishes the contract-refusal codes. A runtime refusal vocabulary would
   either extend that family (`gs.auth.*`) or stay with the Auth producer. This
   is a source-ownership decision for coordinator-1, not a Core implementation
   decision.
2. **Duplicate scope** — whether a UAC number must be unique within a scenario
   only (the current grammar) or within a story. The proposal enforces the
   scenario scope and records the story-scope question.
3. **Alias canonicalization** — whether the Builder migrates its 2,646 alias
   traits to the literal form (one mechanical change in its own scope) or the
   validator resolves the alias forever. The proposal supports both and
   recommends resolving in the validator, so the alias stays legal.
