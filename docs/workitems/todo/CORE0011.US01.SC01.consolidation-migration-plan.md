## The request

The user authorized consolidating Core and Plugins so that only one central
repository remains, and the working direction is Core-central. The user named a
second Core-central direction afterwards: backend-only Core plus a
`Core.Frontend` layer, with the shared Plugins functionality moving into the
appropriate layer and the Plugins lane retaining only its API, App and
product-frontend packages.

This scope inventories all 24 Plugins projects, gives each one a
Core-repository destination under both options, preserves the package and API
boundaries and the exact consumer pins, defines the migration, rollback and
retirement acceptance, and compares the two options.

## The rule that shapes the plan

A package identity has exactly one producer at a time. The feed keeps every
published generation, so a consumer pin never breaks because of a repository
move; it breaks only if a producer publishes a different public surface under
the same identity, or if two producers publish the same identity at once.

Three rules follow, and every cut obeys them:

1. The **identity is preserved**. A moved project keeps its package id, its
   assembly name, its namespace, its public API and its version line. The Core
   repository becomes the producer of `LowlandTech.Plugins.*`; it does not
   become a second producer.
2. The **producer handoff is exclusive**. The Core repository publishes the
   first Core-produced generation of an identity, and the Plugins repository
   publishes nothing for that identity from that point on.
3. The **previous generation stays**. Every generation published before the
   move stays in the feed with its digest unchanged, so every existing exact
   pin keeps resolving.

## The boundary and pin rules

- The package id, the assembly name, the namespace and the public API move
  unchanged. A moved package publishes the same public type names and the same
  public members, measured from the assembly metadata.
- The declared dependencies move unchanged, including the exact contract pin of
  `LowlandTech.Plugins.Domain` on `LowlandTech.Core.Contracts`. The
  consolidation does not change the contract generation that the Domain
  package declares.
- The version line moves with the producer. A Core-produced generation of an
  identity continues that identity's version line; it never restarts it.
- The consumer pins never break. Every published generation stays available
  with its digest, so an exact pin keeps resolving after the move. The
  identities stay as well, so no public type moves. What changes is the
  producing repository and therefore the published version, so the measured
  consumer packages repin once, to the first Core-produced generation. That
  repin is the cost of the move and it is counted per cut.
- `LowlandTech.Core` and `LowlandTech.Core.Contracts` stay in their own
  producers, `core/src/lib` and `core/src/contracts`. The consolidation does
  not merge a plugin package into a Core package identity.

## The second Core-central option — backend-only Core plus Core.Frontend

The user named a second Core-central direction: Core keeps the backend and the
shared library and gains a `Core.Frontend` layer that carries the browser-only
surface, the shared Plugins functionality moves into the appropriate layer, and
the Plugins lane retains only its API, App and product-frontend packages.

### What is browser-only, measured

Core has no browser-only surface today. The repository holds five projects and
no browser asset:

| Core project | Kind |
|---|---|
| `src/lib/LowlandTech.Core.csproj` | the canonical producer |
| `src/contracts/LowlandTech.Core.Contracts.csproj` | the data-only contract |
| `src/test/LowlandTech.Core.Tests.csproj` | the acceptance suite |
| `src/consumer/Consumer.csproj` | the isolated package-only consumer |
| `src/consumer/ContractsConsumer/ContractsConsumer.csproj` | the isolated contract consumer |

There is no `.razor`, `.cshtml`, `.html`, `.js` or `.ts` file in `core/src`. The
browser-only surface that exists in the workspace is in the Plugins UI
packages and in the Builder browser client. `LowlandTech.Core.Frontend` is
therefore new surface, not a move, and it can only carry something if the
browser-only Plugins packages move into it.

### The cost of the second option

The frontend layer keeps the three existing identities, so the 346 consumer
packages of `LowlandTech.Plugins.Blazor` (298) and
`LowlandTech.Plugins.Management.Blazor` (48) repin once, exactly as under the
first option, and no public type of them moves. The difference is that the
Plugins lane survives with three projects instead of none, and that the Core
repository ends with a browser-only layer that it did not have before.

If the frontend layer is instead a **new** package identity, for example
`LowlandTech.Core.Frontend` as a bundle that references the three versioned
packages, then the 346 consumer packages have to move to that identity, which
is a second move on top of the repin that the first Core-produced generation
already costs. A bundle that aggregates the versioned packages behind one id
is still the better shape for a host that pins five to eight independently
versioned packages: it removes the skew from the host without merging
identities or moving public types. The bundle publishes no type of its own
beyond its own metadata, and the decision to publish it is a contract
publication decision that belongs to the cut table of `CORE0010`.

### The comparison of the two options

| | Option 1, the full move | Option 2, backend Core plus Core.Frontend |
|---|---|---|
| Projects moved | 24 | 21 |
| Identities the Core repository produces | 17 plus the two Core identities | the same 17 plus the two Core identities |
| Identities that change | 0 | 0 |
| Consumer packages that repin once with the first Core-produced generation | 1696 distinct packages, 2090 counted per identity | the same 1696, of which 346 sit on the frontend layer |
| The Plugins lane after the migration | retired | retains the API, App and product-frontend packages |
| Browser-only surface in Core | yes, three identities | yes, three identities |
| The retirement cut | required | not required |
| Core estimate | 47 over six cuts | 44 over six cuts, and no retirement of the Plugins repository |
| Residual risk | the Plugins repository has no successor for its API and App hosts, so those two move too | the workspace keeps two repositories and the boundary between them has to be stated in both |

The recommendation stays with the first option for the consolidation itself,
because it ends with one central repository as the user asked, and the
difference in cost is small. The second option carries one real advantage that
the first does not: the API host, the App host and the product frontend keep a
home in the Plugins lane, which is the only part of the Plugins lane that
never was a shared library. If the user prefers to keep those three in the
Plugins lane, the second option is the one to execute, and the frontend layer
keeps the three existing identities.

## The triage of the Composition proposals, and the corrections of 2026-11-02

coordinator-1 asked Core to triage the Core-owned cuts of `COMP0005` and
`COMP0006` into `CORE0010` and this scope.

**`COMP0005` is covered by `CORE0010`.** Its Core-owned cuts are the transition

**`COMP0006` is covered by this scope.** Its Core-owned cut is the browser-only

the identities and the migration gates are in the second option above, and the
decision to publish a bundle identity is a contract publication decision that
belongs to the cut table of `CORE0010`.

The Plugins lane measured two corrections against this scope on 2026-11-02 and
both are applied:

1. The project count. The mapping table moves 21 projects under the second
   option, because the API, the App and the product-frontend projects stay in

   say 21. All 24 move under the first option.
2. The pin effect. The identities stay and no public type moves, but the
   producing repository and the published version change, so the measured
   consumer packages repin once with the first Core-produced generation. The
   comparison table now records that repin instead of claiming that no pin

## The acceptance

### Migration acceptance

For every moved identity:

1. The Core-produced package declares the same package id, the same assembly
   name and the same declared dependencies as the last Plugins-produced
   generation.
2. Its public surface equals the public surface of the last Plugins-produced
   generation, compared from the assembly metadata: the same public type names
   and the same public members, with no added and no removed member.
3. The isolated package-only consumer restores it alone and resolves exactly
   one version of every dependency, with no source checkout reference in the
   comparison.
4. The trim analysis of the moved package reports 0 warnings and 0 errors.
5. Every published generation that existed before the move is still in the feed
   with its recorded digest unchanged, and every consumer pin of the identity
   still resolves.

### Rollback acceptance

1. The Plugins repository can publish the next generation of the identity from
   its last state, proven by a dry-run publish into a scratch feed; a rollback
   never overwrites a published version.
2. The Core repository can drop the moved source and its publication script
   without any published artifact changing, because the first Core-produced
   generation is immutable and stays available.
3. A cut is reverted before the next cut starts; a published Core generation is
   never withdrawn from the feed.

### Retirement acceptance

1. The Plugins repository publishes no further generation of any moved
   identity, and its publication tooling for those identities is removed in the
   same change that stops it.
2. The last Plugins-produced generation of every moved identity stays in the
   feed with its digest unchanged.
3. The Core repository holds the source, the producer scripts and the test
   layout of every moved project, and no moved project remains referenced from
   the Plugins repository.
4. The Plugins repository is archived with a record of the last generation it
   published for every identity.
