# M5-005 - Separate support files from scenarios in the layout gate

- **Milestone:** M5
- **Status:** proposal
- **Priority:** P2
- **Owner:** core
- **Source owner:** core
- **Coordinator:** coordinator-1
- **Depends on:** M5-001
- **Scope delivered:** CORE0016-US01-SC01
- **Specification:** CORE0016.ScenarioDiscovery
- **Phase:** created 2026-11-26 at the coordinator's request to retain the discovery limitation of the layout gate as a separate Core item; the proposal records the rule, the measured example and the bounded fix, and implements nothing

## The limitation

`eng/verify-test-layout.py` decides whether a file is a scenario with
`_is_scenario`: a file that declares `[UserStory]`, `[Given]`, `[When]` or
`[Then]` anywhere is a scenario and is held to the scenario rules — the path
`<SCOPE>.<Area>/US##.<Story>/SC##_Name.cs`, a class named `SC##_Name`, one named
type and the length limit.

A support file that declares one of those attributes for a different purpose is
therefore classified as a scenario and rejected for its path and class name,
even though it is not a scenario. The clearest prospective case is the
browser-aware base of M5-004: a shared base that declares `[Given]`/`[When]`
attributes for its subclasses would be flagged with no path that could satisfy
the rule, because a base class is not a scenario.

## The measured example

`story-editor/src/test/Infrastructure/Architecture/LaneBoundary.cs` is measured
as a scenario and reported with `invalid-scenario-path` and
`invalid-class-name`:

```
python core/eng/verify-test-layout.py --root story-editor/src/test --json
→ Infrastructure/Architecture/LaneBoundary.cs: invalid-scenario-path, invalid-class-name
```

The example is ambiguous, and the proposal records that rather than overclaiming:
the file declares `[UserStory]`, `[Then]` steps, `[Fact]`s and UAC traits, so it
may be a genuine acceptance scenario that lives at a non-canonical path, in
which case the finding is correct and the repair belongs to its lane. It is not
proof that a support file is misclassified; it is proof that the gate cannot
distinguish the two shapes.

## The proposed rule

A file is a scenario when **either** condition holds:

1. it declares `[UserStory]`; or
2. it declares a named type that matches `SC##_ScenarioName`.

A file that only declares `[Given]`, `[When]` or `[Then]` attributes — a base
class, a helper or a shared fixture — is support: it is inventoried as legacy
support (or ignored) and is not held to the scenario path, class-name or
single-type rules. The Facts inside a scenario file keep every rule unchanged.

Consequences:

- a real scenario keeps `[UserStory]` and stays measured, so the rule cannot be
  used to hide a scenario;
- a browser-aware base that only carries the step attributes stops being
  reported;
- the ambiguous `LaneBoundary.cs` stays a finding while it declares a
  `[UserStory]`, and its lane decides whether to move it to a scenario path or
  drop the story attribute.

## Detection limits

- The rule still cannot tell a base class that declares `[UserStory]` from a
  scenario; the base must not carry a story attribute, which the M5-004 contract
  already says (the browser form's story attributes belong to the scenario).
- The gate remains a source-shape check; it proves neither that the support file
  is used nor that a scenario ran.

## Adoption and impact

- The rule changes the Core gate only; no lane is scanned by default and no
  consumer gate is created.
- Measured impact on the trees this lane has scanned: the Story Editor tree
  reports 284 scenarios and 1,313 findings today; the rule would remove the two
  findings of a support file that carries no `[UserStory]`, and would keep the
  `LaneBoundary.cs` findings while its `[UserStory]` stays. The Core tree reports
  13 scenarios and 0 findings before and after.
- The negative fixture set gains one fixture: a support file with step
  attributes and no story attribute is accepted; a scenario without a story
  attribute but with an `SC##_` type is still measured.

## Risks

- **A scenario hides by dropping `[UserStory]`.** Mitigated by rule 2: the
  `SC##_` type alone still makes the file a scenario, and the layout still
  rejects a path or class that does not match.
- **A lane relies on the old classification.** The gate is Core-owned and no
  lane opts in yet; the change is recorded with its measured impact.

## Verification and recovery

- Verification: the fixture matrix keeps every existing rule; the new positive
  fixture is accepted; the Core tree keeps 13 scenarios and 0 findings; the
  Story Editor measurement is recorded before and after.
- Recovery: the rule is one predicate in `_is_scenario`; reverting it restores
  the current classification and changes no production code.
