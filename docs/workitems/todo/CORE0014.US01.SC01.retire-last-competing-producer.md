## The blocker

M2-001 (`CORE0001-US02-SC01`, UAC01) cannot close while one checkout outside
this repository can still publish the `LowlandTech.Core` identity. The Core-owned
half is delivered and repeatable; the remaining half is the Foundry retirement,
and it has not moved since 2026-10-25. The lane has re-measured it on every pass
since 2026-11-17 without a change, which is the condition the shared workflow
asks a proposal for.

  updated since 2026-10-25.
- The `develop` checkout itself already carries the retirement commit
  `134299084`, and its own `src/core` refuses a forced pack. The worktree simply
  predates that commit.

## Why Core cannot close it

The remaining actions all touch a checkout this lane does not own:

- removing the worktree registration edits the Foundry clone's worktree
  metadata and removes another worker's checkout;
- merging the pull request changes the Foundry repository's `develop`;
- repointing the worktree onto the retirement commit rewrites another lane's
  branch state.

The workspace rules forbid a lane from removing, switching, resetting or
rewriting another worker's checkout. Core can measure the state and name the
recovery; it cannot perform it.

## The options

| # | Option | Owner | Bounded action | Verification |
|---|---|---|---|---|
| A | Merge PR #185, then remove the worktree | foundry owner, coordinated by coordinator-1 | review and merge the single retirement commit; then `git worktree remove .worktrees/agent3` on the clean worktree (the branch stays on origin) | producer gate exits 0 with no competing producer; M2-001 UAC01 ticks |
| B | Remove the worktree without merging | foundry owner | `git worktree remove .worktrees/agent3`; PR #185 stays open for the retirement record | the gate reports the worktree gone; `develop/src/core` is already retired, so UAC01's competing-producer half is met while the PR stays a review item |
| C | Make the worktree non-publishing | foundry owner | apply the retirement commit (or `IsPackable=false` plus `RejectRetiredCoreProducer`) to `feature/agent3` | the gate reports the checkout retired; the branch is not rewritten, a new commit is added |
| D | Accept the producer as in-scope | nobody | would weaken UAC01 and let a second producer of the canonical identity remain | rejected: it contradicts the cutover and the published package identity |

Decision criteria: A is the complete retirement and the preferred path; B is the
smallest action that satisfies the Core-owned invariant while the review
continues; C keeps the branch history and is the right choice if `feature/agent3`
is still wanted for work; D is not a candidate.

## Dependencies and scope

- No Core implementation follows from this proposal. It creates no dependency
  edge, no approval gate and no change to M2-001's acceptance.
- The pull request and the worktree belong to the Foundry repository owner;
  coordinator-1 owns the routing and the GitHub reconciliation.
- The Core gate `eng/verify-producers.py` and the acceptance Fact of M2-001 stay
  the authority; no criterion is relaxed.

## Risks

- **Removing a worktree with uncommitted work.** The measured worktree is clean
  today; the owner re-checks before removal. The branch survives on origin.
- **Merging a stale retirement commit.** PR #185 is one commit on a branch four
  weeks old; its owner re-verifies the merge against the current `develop`
  before merging.
- **A new worktree reappearing.** The gate is repeatable, so a later checkout
  that publishes is measured again; the retirement commit plus the worktree
  removal is the durable fix.

## Verification and recovery

- Verification of any option: `python core/eng/verify-producers.py
  --repository-root D:/lowlandtech/core --workspace-root D:/lowlandtech` exits 0
  and names no competing producer; then M2-001 reopens, re-runs the gate and the
  closure gate, ticks UAC01 and closes the cutover.
- Recovery: the worktree can be re-added from `origin/feature/agent3`; the
  retirement commit is already on `develop` and is not reverted by the worktree
  removal; the pull request can be reopened or re-reviewed.
