### Core assessment — EF Core and legacy plugin abstraction consumer inventory — 2026-10-27

Report only. No API is removed, no dependency is dropped and no item is claimed;
the row stays blocked and unrefined.

**Where the EF Core dependency comes from.** `src/lib/LowlandTech.Core.csproj`
carries a direct `Microsoft.EntityFrameworkCore 10.0.9` reference and
`src/lib/GlobalUsings.cs` has a global `using Microsoft.EntityFrameworkCore;`.
The EF-bound public surface is confined to `src/lib/Plugins/`:
`DbFactoryContext<TContext>` (binds `IDbContextFactory<TContext>` and
`DbContext`), `IDbFactoryContext` and `DbContextService`. The neighbouring
`IPluginContextFactory`/`IPluginContextRegistry`/`PluginContextDescriptor`/
`PluginContextFactory` family, `IGraphContributingPlugin.SyncedDbContextTypes`
and `PluginDescriptor.DbContextType` carry only `Type` values and bind no EF
type in their signatures.

**Actual consumers, measured in the workspace on 2026-10-27:**

| Consumer | How it reaches the surface | EF exposure |
|---|---|---|
| Builder | own local copies in `builder/src/shared/core/Plugins/` | insulated from the package |
| Foundry (`develop`) | own local copies in `develop/src/core/Plugins/` | insulated; that copy is build-only |
| Harness | references the Core package `[2026.10.2-202610242]`; no `IDbFactoryContext`/`DbFactoryContext` use found in `harness/src` | inherits the transitive EF dependency only |
| Components | references the Core package; no `IDbFactoryContext`/`DbFactoryContext` use found in `components/src` | inherits the transitive EF dependency only |
| Backend | consumes no Core package | none |

No package consumer of `IDbFactoryContext`, `DbFactoryContext` or
`DbContextService` was found. The retirement risk sits in the package closure
that every Core consumer inherits, not in a call site.

**Legacy plugin abstractions.** `IApiPlugin`, `IAppPlugin`, `PluginDescriptor`,
`PluginDiscovery`, `PluginHostService`, `PluginRegistry`/`IPluginRegistry`,
`IPluginDependencyResolver`, `IApiPluginSource` and `IGraphContributingPlugin`:

- Harness is the package consumer. `IAppPlugin` is used in
  `harness/src/app/Program.cs`, `harness/src/shell/ShellComposition.cs`,
  `harness/src/shell/ShellServiceExtensions.cs` and
  `harness/src/infrastructure/Factories/AppFactory.cs`; `IApiPlugin` and
  `PluginDescriptor` are used across
  `harness/src/test/SPEC2050.PluginFramework/**` and
  `harness/src/test/HARN0003.Extensions/**`.
- Harness also carries forked copies under `LowlandTech.Harness.Core.Plugins`
  in `harness/src/core/Plugins/` (`IFeaturePackage`, `IFeatureSettingsProvider`,
  `FeatureDescriptor`, the registries). That is a different namespace, so the
  package and the fork do not collide.
- Builder and Foundry carry local copies and are insulated.
- Components uses only its own `SessionPluginDescriptor`, not the Core plugin
  descriptor. The Backend has its own lineage
  (`LowlandTech.Graph.Core.Contracts.PluginDescriptor`).

**Proposed versioned extraction and compatibility path.**

1. Split EF out first, because it is the only dependency every Core consumer
   inherits. Publish `LowlandTech.Core.EntityFrameworkCore` with its own
   version line, carrying `IDbFactoryContext`, `DbFactoryContext<TContext>` and
   `DbContextService` in the same `LowlandTech.Core.Plugins` namespace, and
   declare `TypeForwardedTo` in `LowlandTech.Core` so the namespace and the
   type identity stay stable. `LowlandTech.Core` then drops the EF reference.
   Consumers that use those three types must add the new package reference;
   the consumers measured above use none of them and only lose the dependency
   from their closure.
2. The plugin and graph contracts move in the same shape through M3-002
   (`LowlandTech.Core.Contracts`), the row that already owns the portable
   plugin contribution contract. The legacy plugin shapes stay published by a
   compatibility package until Harness and the local-copy owners migrate.
3. Consumer migration stays with the consumer owners: Components owns its batch
   closure (M2-001 UAC02), Builder and Coder own their adopted pins (UAC03),
   Harness owns its pin and its M8-007/M11 proofs.
4. Exit action for this row: UAC02 becomes true after the EF package is
   published and every supported consumer has migrated. Until then the
   remaining EF dependency and its exit action stay explicit and UAC02 stays
   open.
5. The Core-only consumer (`src/consumer`) proves that the trimmed package
   keeps the graph registry, the plugin descriptor defaults and the
   `ComponentsStartupMap` contract. It carries no EF type, so the split does
   not weaken that proof.
