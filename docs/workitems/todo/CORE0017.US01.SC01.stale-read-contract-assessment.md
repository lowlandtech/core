# M7-001 - Assess the stale-revision clause of the generic read contract

- **Milestone:** M7
- **Status:** proposal
- **Priority:** P2
- **Owner:** core
- **Source owner:** core
- **Coordinator:** coordinator-1
- **Depends on:** None
- **Scope delivered:** CORE0017-US01-SC01
- **Specification:** CORE0017.StaleRead
- **Phase:** created 2026-11-27 on the coordinator's cross-lane finding; the assessment is the deliverable and the recommendation is to keep the contract unchanged

## The question

Coordinator-1 relayed a finding from two consumers of the generic read contract
(`20261127T162751793854Z-38bfcdeb@coordinator-1`, source
`src/lib/Abstractions/IGraphSession.cs`):

- Backend `BKPL0029` (#155) and Builder `CANS2100-US63-SC01` both ask for a
  **stale-revision read refusal** through `IGraphSession.GetAsync`.
- `IGraphSession.GetAsync` has no expected-revision input, so a consumer cannot
  pass the value that would be stale and the host has nothing to compare.
- Backend can prove the returned identity and revision but cannot reject a stale
  expected value it never receives.

The request is to assess whether stale-read rejection is intentionally outside
this generic read contract, and to coordinate the honest semantics with Backend
and Builder.

## The measured contract

`src/lib/Abstractions/IGraphSession.cs` (25 lines) declares five typed and five
untyped members. None of them accepts a revision, an expected version, an ETag or
a concurrency token:

```csharp
Task<T?> GetAsync<T>(Guid id, Func<IQueryable<T>, IQueryable<T>>? query = null, CancellationToken ct = default) where T : class;
Task<object?> GetAsync(Type entityType, Guid id, CancellationToken ct = default);
```

The same holds for `ListAsync`, `AddAsync`, `UpdateAsync` and `DeleteAsync`: the
only inputs are the identity, an optional query shape, the entity and a
cancellation token. The interface is a session-scoped data-access surface, not a
versioned-read protocol.

Where a revision does live in this workspace, it lives on the entity or the
document projection (`Node.Revision`, the CORBIS `document` head), not on the
session contract. A stale read is therefore an application-level
check-then-write concern (`UpdateAsync` with a carried revision, or a
compare-and-set at the projection that owns the head), not a read refusal.

## The assessment

**Stale-read rejection is intentionally outside the generic read contract, and
the contract should not be expanded for it.** Four reasons, each measured:

1. **A read has no expected value to be stale against.** `GetAsync(id)` answers
   "what is stored for this id in this session". Staleness is a property of a
   *caller's belief* about a revision, so the caller must supply it; the contract
   deliberately takes only the identity. Adding an expected revision to a read
   would turn every read into a conditional read and change the meaning of every
   existing call that passes nothing.
2. **The refusal a consumer actually needs is the write-side one.** Both named
   consumers want the stale case so that a lost update is visible. That is
   `UpdateAsync` refusing a carried revision behind the stored one, or the
   projection refusing a stale head with `409` — the Backend already does the
   latter for `PUT api/documents/{nodeid}` with a content-hash causal head.
   Putting it on the read gives the caller a refusal for a read it did not
   intend to reject.
3. **The contract has no revision vocabulary to carry it.** `IGraphSession` is
   generic over `T : class` and says nothing about revisions; a second overload
   would either add a revision abstraction to Core that no other consumer uses,
   or hard-code "revision" into a surface that also serves entities without one.
4. **A concrete generic need was not demonstrated.** The finding shows two
   consumers wanting it, and both are satisfied by their own write-side or
   projection check. No consumer has a generic, entity-agnostic operation that
   is only expressible as a conditional read.

**Recommendation: no contract expansion.** If a generic need ever appears, it
belongs in its own approved workitem that names the revision abstraction, the
affected consumers and the compatibility story; it is not a refinement of this
finding.

## The honest semantics for the two consumers

The three refusals are not equally expressible, and each consumer should state
which of them its criterion actually observes:

| Case | Expressible through `IGraphSession.GetAsync`? | What to assert instead |
|---|---|---|
| wrong type | yes — the caller compares the answered type to the requested one | the answered entity's type is the requested type, and a type mismatch is answered `null` rather than a partial entity |
| foreign session | yes, at the host boundary | a node the session does not hold is refused by name with no data |
| stale revision | **no** — nothing to compare | move the case to the write path (`UpdateAsync` / projection `409`) or record it as not applicable to this contract |

Backend has already recorded Option A for `BKPL0029` UAC03: the stale case is
recorded as not applicable, the foreign-session refusal is the enforced one, and
the wrong-type case is the consumer's comparison. That disposition matches this
assessment and needs no Core change.

## Coordination

- coordinator-1: the assessment and the recommendation, with the measured
  signature and the per-case table.
- backend: the confirmation that its Option A disposition is the correct one and
  that no Core change is coming, so its UAC can close on the two expressible
  cases.
- builder: the same, for `CANS2100-US63-SC01` UAC02, with the explicit note that
  the stale case is not expressible and the write path is where it belongs.

## Risks

- **A consumer claims the stale case anyway.** The table above names what is
  observable, so a claim would be visible against it.
- **A future generic need is suppressed by this decision.** The recommendation
  does not forbid a separate workitem; it forbids adding the case to an existing
  read contract without one.

## Verification and recovery

- Verification of the assessment: the recorded signature of
  `IGraphSession.GetAsync` is unchanged, the two consumers record their
  dispositions in their own source, and no Core source changes.
- Recovery: none needed — nothing is implemented. If a later approved workitem
  adds a conditional read, this proposal records the baseline it starts from.
