## Outcome and scope

State the capability admission semantics of the canonical transition contract
and own the delivery of that statement: distinguish the host that declares no
capability registration from the host that registers none, document the
obligation of a host, and deliver the correction as a new immutable contract
version without changing the published one.

This scope does not change the schema, the members, the triggers or the
effects of `gs.transition/v1`, and it does not change the canonical bytes of a
document. It corrects the admission rule and the documentation that describes
it.

The question came from the Composition lane, which observed that a host that
registers no capability admits any declared capability and cannot express "this
host trusts nothing" through the admission request.

## The Core decision

**An absent registration and an empty registration are different cases, and the
empty registration must refuse every declared capability.**

The rule as written cannot express the difference:

```csharp
if (knownCapabilities is null || knownCapabilities.Count == 0) return;
```

That single early return covers both cases, so a host that registers nothing is
treated like a host that told the contract nothing at all. The two cases have
different meanings:

| The host passes | The meaning | The rule |
|---|---|---|
| no registration (`null`) | the host declines to constrain the capability, and the contract cannot check what it was not told | no capability refusal |
| an empty registration | the host registered no capability, so every declared capability is unregistered | refuse with `gs.contract.capability.unknown` |

The empty case is the meaning the contract already states elsewhere. The
refusal `gs.contract.capability.unknown` says that a capability "is not
registered", and `CapabilityReference` states that "a data-defined plugin binds
to a capability that is already registered and never registers one". A host
that registered nothing has registered nothing, so the declared capability is
not registered and the refusal applies. The reader of the contract is right:
the current rule is a gap in the canonical admission rule, not a designed mode
that trusts everything.

The composition lane's own binding rule is therefore stricter than the
canonical rule on purpose, and it stays correct until this scope delivers the
correction.

## The measured consumer impact

The rule was measured across the workspace on 2026-10-30:

| Consumer | How it reaches the rule | What it passes |
|---|---|---|
| composition | `composition/src/lib/Binding/ContractBinder.cs` calls `TransitionContractValidator.Admit` | a non-null registration, and it applies its own stricter binding rule with the refusal `capability.not-registered` |
| core | the acceptance of the graph contract calls `TransitionContractValidator.Admit` | a non-empty registration |
| backend | no call to the canonical admission | none |
| harness | no call to the canonical admission | none |

No caller passes no registration and no caller passes an empty registration, so
the correction has no live consumer impact. The measured consequence is that
the contract, not the host, will refuse an unregistered capability once the
correction ships, and the hosts that already refuse it keep their own rule
until they prove the new version.

## The delivery boundary

The correction is a behavior change of a published contract, so it ships as a
new immutable `LowlandTech.Core.Contracts` version:

- The published version stays available and unchanged, and no published
  version is overwritten.
- The hosts that call the rule are notified with the new version, and the
  consumer pins move with their own source-owned scopes.
- The canonical bytes of a transition document do not change, so no content
  hash and no parity fixture changes.
- The Core package and its closure are untouched by this correction.

The Composition lane asked whether the empty registration is an intentional
"unrestricted" mode and, when it is not, whether the consumer contract differs
from the wording of a required capability.

The Core answer: the consumer contract is right and the rule has a gap. The
empty registration must refuse every declared capability, the absent
registration stays the only case that does not constrain, and the correction
ships as a new immutable contract version that leaves the published one
available. Until that version is published, the Composition binder keeps its
own stricter binding rule, which is correct under both readings.
