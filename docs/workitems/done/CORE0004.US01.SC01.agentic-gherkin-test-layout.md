## Outcome and scope

Make `src/test` follow the shared agentic-gherkin Given/When/Then acceptance layout while preserving the existing Core contract, trim, graph and package-consumer regression behavior. This is a test migration; it does not change Core production APIs or certify any open M2/M3/M4 acceptance criterion.

## Current gap

`CoreContractsTests.cs`, `CoreTrimmingAcceptanceTests.cs` and `GraphContractAcceptanceTests.cs` use broad xUnit classes and multi-assertion Facts. They do not have story/scenario paths, one Given and one When per scenario, or uniquely tagged, single-observation UAC Facts. The Core engineering adapter documents that no native scenario layout checker currently exists. Preserve the existing five Backend parity fixtures and all current test identities/evidence while mapping them to the shared grammar.

## Acceptance criteria

- [x] UAC01: Inventory every existing Core test and its source workitem/UAC or regression purpose before moving it; retain all accepted behaviors, fixtures and traceability without renumbering existing acceptance identities.
- [x] UAC02: Core scenarios use story/scenario files, one Given, one When, a captured result and one direct Shouldly assertion per uniquely tagged UAC Fact; shared mechanics live in reusable fixtures/use cases and do not duplicate production behavior.
- [x] UAC03: A Core-owned layout gate detects invalid scenario paths, missing/duplicate UAC traits, extra Given/When steps, multiple assertions and empty or skipped selections. Wire it into Core's documented verification commands without claiming another lane's checker as Core proof.
- [x] UAC04: The migrated suite executes the same contract, trim and Backend parity behavior against production code, with exact selected/executed/skipped Fact counts and no loss of existing regression coverage.
- [x] UAC05: Core build, focused tests, package preflight and the Core-only trimmed consumer remain green; record exact command exits and package/consumer evidence. No package publication is implied by this test-layout work.

## Implementation — 2026-10-29

### The Core owned layout gate

`eng/verify-test-layout.py` scans the test sources of the repository and
reports every violation of the shared agentic-gherkin layout. A file that
declares a user story or a Given, When or Then step is a scenario and is held
to the layout rules; the other test files are the retained legacy classes and
are inventoried without being held to the scenario rules. The rules are the
path of the scenario file, one Given and one When, the grammar of the Then
step, the UAC trait, the single expression-bodied assertion, the selection and
the unfinished skip, the class name, the number of named types and the length
of the scenario.

The gate is wired into the documented verification commands of the lane:
`coordinator.ps1 -Command verify-test-layout` in the shared profile and the
Core adapter of the shared engineering skills. The adapter no longer states
that the lane has no native scenario layout checker.

### The negative fixtures

`eng/test-layout/fixtures/invalid` holds one fixture per rule, outside the
test tree so that the compiler never sees them. Each fixture breaks exactly
one rule:

`duplicate-uac-trait`, `empty-selection`, `invalid-class-name`,
`invalid-scenario-path`, `invalid-then-step`, `missing-given`,
`missing-uac-trait`, `missing-when`, `multiple-assertions`, `multiple-given`,
`multiple-types`, `multiple-when`, `non-expression-fact`,
`scenario-too-long` and `unfinished-skip`.

Every one of the fifteen fixtures is rejected with its own rule and with no
other rule beside it.
