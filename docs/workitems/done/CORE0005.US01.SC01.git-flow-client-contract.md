## Outcome and scope

Complete the existing Core graph git-flow read contract so Coder SHEL0003-US01-SC01 can render merge requests and feature proposals without inventing states in the shell. Core owns `src/lib/Plugins/MergeRequestStatus.cs`, `GraphMergeRequest.cs`, `MergeRequestProcessor.cs` and `FeatureProposalDocument.cs`. Extend their published models and source-owned transitions while preserving existing persisted documents and package consumers. The Coder lane owns its shell rendering and interaction acceptance.

## Acceptance criteria

- [x] UAC01: The merge-request contract distinguishes Open, Reviewing, Approved, Rejected, Merged and Abandoned with stable wire values. Existing Open/Approved/Rejected documents still deserialize to their original meanings; invalid or terminal transitions are refused by Core rather than hidden by Coder.
- [x] UAC02: The Core processor exposes which live requests may be approved or rejected and prevents those actions after merge, rejection or abandonment. A request can reach the new Reviewing and terminal states through named Core-owned behavior rather than client-side enum assignment alone.
- [x] UAC03: `FeatureProposalDocument` exposes a stable title, lifecycle status and Gherkin specification for Coder's gap surface. Legacy documents lacking those fields have an explicit compatible default or named migration/refusal; submit/discard are available only while Draft.
- [x] UAC04: An isolated package consumer can compile and read the new contract through one immutable `LowlandTech.Core` package pin. Coder proves its SHEL0003 read and action surface separately; Core records that handoff without claiming Coder acceptance.

Preserve existing serialized values and callers rather than renaming or reordering the three published enum members. ### Contract change

- `src/lib/Plugins/MergeRequestStatus.cs` publishes the six states with their
  stable wire values: Open 0, Approved 1, Rejected 2, Reviewing 3, Merged 4,
  Abandoned 5. The three published members keep their original numbers and
  their original names, so a document of the older producer still reads with
  its original meaning. `MergeRequestStatusWireConverter` writes that number
  and reads the number as well as the member name, and refuses a value that
  names no state. `MergeRequestStatusLifecycle` carries the rules of the
  states, so the client that renders a request and the processor that moves it
  read one rule.
- `src/lib/Plugins/MergeRequestProcessor.cs` owns every move between the
  states. `CanApprove`, `CanReject`, `CanStartReview`, `CanAbandon` and
  `CanMerge` expose which live requests may still be answered;
  `StartReviewAsync` moves an open request to Reviewing, `RejectAsync` and
  `AbandonAsync` settle a live request, `MergeAsync` settles an approved
  request as Merged, and `ApproveAsync` keeps its original meaning: it
  replays the proposed transitions, archives the SQLite file and emits the
  legacy merged event. A move that the state does not allow is refused with
  an `InvalidOperationException` instead of being hidden by a client.
- `src/lib/Plugins/FeatureProposalDocument.cs` publishes `Title`, the
  `Status` lifecycle and the Gherkin `Specification`. A document of the older
  producer carries none of the three and reads with a null title, a null
  specification and the Draft status, which keeps it readable and submittable.
  `Submit` and `Discard` are available only while the proposal is a Draft;
  `Accept` and `Reject` move a reviewed proposal.
- `src/consumer/Program.cs` reads the merge-request and the feature-proposal
  lifecycle from the packaged contract, and `eng/build-local.ps1` packs the
  candidate before the tests run, so a test that reads the candidate observes
  the artifact the release publishes, and asserts the two new state lists in
  the report of the trimmed consumer.
