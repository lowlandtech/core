## Outcome

Close the two measured blind spots of the Core-owned layout gate that the M5-002
proposal records, without enforcing anything on another lane:

1. **Alias-aware UAC resolution.** The Builder writes the UAC trait through the
   compile-time constants of `builder/src/testing/LowlandTech.Builder.Testing/Spec.cs`
   (`[Trait(Spec.UAC, "NN")]`), 2,646 times in 678 files. The gate matches only
   the literal `[Trait("UAC", "...")]`, so every one of those Facts reports
   `missing-uac-trait` and the duplicate rule never sees them.
2. **The declared area namespace.** The gate checks the path and the class name
   and never reads the namespace, so a scenario in the global namespace — the
   shape the Backend reported for `CHAN0001` `SC02_DurableInbox` — is still
   reported as a valid scenario.

This scope is Core tooling: the gate, its fixtures and its acceptance family. It
publishes no package, changes no production contract and creates no adoption
gate for another lane. The UseCase result coverage and named refusal reasons of
M5-002 stay with that proposal and its open decisions.

## Acceptance criteria

- [x] UAC01: The gate resolves a UAC trait written through a compile-time
  constant alias exactly like the literal form, and the resolved value feeds the
  existing UAC rules. A positive fixture proves the alias form is accepted with
  no violation, and the Builder-shaped alias is resolved to `"NN"`.
- [x] UAC02: A scenario that repeats a resolved UAC across two Facts is rejected
  with `duplicate-uac-trait`, including when both Facts name the trait through
  the alias. The regression fixture records the PRB-040 shape and the alias
  fixture is rejected with that code and no other.
- [x] UAC03: A scenario that declares no namespace is rejected with
  `missing-namespace`, and the finding names the file.
- [x] UAC04: A scenario whose declared namespace does not carry the
  `<SCOPE>.<Area>.US##.<Story>` identity of its path is rejected with
  `namespace-area-mismatch`, and a namespace that carries it is accepted.
- [x] UAC05: A trait key that resolves to no declared constant is rejected with
  `unresolved-trait-key` instead of being accepted or reported as a missing UAC.
- [x] UAC06: The Core tree keeps zero violations, the gate stays wired into the
  documented `verify-test-layout` command and every negative fixture keeps its
  exact rule outcome (eighteen after this scope).

## Refinement state

Refined is true. The contract of each check, its finding code and its fixture is
recorded in the M5-002 proposal and repeated in the acceptance criteria above.
The alias table is the set of compile-time string constants declared in the
scanned root, so the gate stays self-contained and names no lane's project. The
namespace rule derives the expected identity from the scenario path, so it
accepts the Core, Backend, Builder and Harness namespace prefixes without a
per-lane configuration.

Detection limits, stated so the acceptance cannot overclaim:

- only compile-time `const string` declarations are resolvable; a run-time
  expression is reported as `unresolved-trait-key` and never silently accepted;
- the duplicate rule is per scenario, which is the grammar's scope;
- the namespace rule proves the declaration and the identity of the path; it
  does not prove that a filter selects the scenario.

## Evidence

### The delivery — 2026-11-18

The gate gained the alias resolver, the attribute-block read and the namespace
rule; the acceptance family and the fixtures prove each of them against the real
gate.

**The attribute block is read, not only the Fact line.** The Builder writes the
attributes of a Fact on separate lines:

```csharp
[Fact(DisplayName = "UAC01: ...")]
[Trait(Spec.UAC, "01")]
[Given("...")]
```

A gate that reads only the line of the `Fact` cannot see that trait, whether the
key is an alias or a literal. `_facts_of` now reads the contiguous attribute
block around the declaration, so the trait is found in both shapes and the
existing same-line form keeps working.

**The alias resolves through the declared constants, then the canonical keys.**
`_resolve_trait_key` reads a literal as its own value, reads a dotted or plain
name from the `const string` declarations of the scanned root, and falls back to
`UAC` and `Spec.UAC` so the Builder shape resolves even when its `Spec.cs` lives
outside the scanned test root. A key that resolves to nothing is reported as
`unresolved-trait-key` and is never counted as a missing UAC.

**The namespace rule derives its expectation from the path.**
`_expected_namespace_suffix` builds `<SCOPE>.<Area>.US##.<Story>` from the
scenario path and the declared namespace must end with those segments. The rule
therefore accepts the Core, Backend, Builder and Harness prefixes without a
per-lane configuration. A missing namespace is `missing-namespace`; another
identity is `namespace-area-mismatch`. A file whose path is already invalid is
not also reported for its namespace, so one broken rule stays one finding.

**The fixtures.** The three new negative fixtures live beside the fifteen:

| Fixture | Rule it breaks | Reported |
|---|---|---|
| `invalid/missing-namespace` | no namespace declaration | `missing-namespace` only |
| `invalid/namespace-area-mismatch` | namespace names `OtherArea` | `namespace-area-mismatch` only |
| `invalid/unresolved-trait-key` | `[Trait(Keys.UAC, "01")]` names no constant | `unresolved-trait-key` only |
| `invalid/duplicate-uac-trait/CORE0013...` | two alias Facts repeat `Spec.UAC "04"` | `duplicate-uac-trait` at the second Fact |

The positive fixture `valid/alias-uac-trait` is accepted with one scenario, no
violation and a resolved UAC of `01`. The existing fifteen fixtures keep their
exact codes, and the M5-001 acceptance that walks them keeps passing.

### Reopened for the isolated-output defect — 2026-11-19

Coordinator-1 accepted the delivery and then reported that the six focused Facts
fail when the test binary runs from an artifacts path outside the repository
(`20261118T131500134364Z-4f083110@coordinator-1`, source
`src/test/CORE0013.TestLayout/US01.Grammar/UseCases/GrammarChecksUseCase.cs`).
The report is correct and it is reproduced here:

```
dotnet test --project src/test/LowlandTech.Core.Tests.csproj -c Release
  --filter-class "*SC01_TheGrammarResolvesAliasesAndTheNamespace*"
  --artifacts-path D:/lowlandtech/.tmp/core/core/artifacts
```

exits 2 with 6 failed and 0 succeeded, and every Fact reports "The repository
root was not found."

The cause is the discovery of the repository root: `GateRunner.RepositoryRoot`
walks up from `AppContext.BaseDirectory`, which is the artifacts output
directory when `--artifacts-path` is used, so it never reaches
`eng/verify-test-layout.py`. The default output directory happens to sit under
the repository, which is why the earlier run passed.

The repair keeps the acceptance the same and makes the discovery explicit:

1. `GateRunner.RepositoryRoot` reads an explicit root from the
   `LOWLANDTECH_REPOSITORY_ROOT` environment variable first, then walks up from
   the current working directory, then from the base directory, and only from
   the base directory when neither carries the marker.
2. `GrammarChecksUseCase` additionally accepts a root that carries the marker
   but no `src/test` directory of its own, so a copied or linked tree is still
   measured when the caller names it.
3. The isolated-output acceptance is the verification command of this repair,
   and the default-output run and the full suite stay required.

This edit is a source-owned repair of the same scope, so the item returns to
`doing` before the change and closes again with both runs recorded.

### The repair delivered — 2026-11-19

The defect is fixed and both the isolated and the default acceptance pass.

**The root no longer depends on the runtime directory.**
`src/test/LowlandTech.Core.Tests.csproj` writes the repository root into the
test assembly as `AssemblyMetadata("RepositoryRoot", ...)`, and
`GateRunner.RepositoryRoot` resolves in this order:

1. the `LOWLANDTECH_REPOSITORY_ROOT` environment variable, when it names a root
   that carries the marker — the explicit override the report asked for;
2. the build-time root embedded in the assembly;
3. the current working directory and its ancestors;
4. the base directory and its ancestors.

Every candidate must carry `eng/verify-test-layout.py` and `src/test` before it
is trusted, so a stale embedded path falls through instead of measuring the
wrong tree. `GateRunner.CarriesMarker` holds that single check.
